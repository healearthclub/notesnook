November 21, 2026. Coordination review for US-MONOGRAPH-PUBLISHING-01, against `heal-earth-club/docs/monograph-publishing-contract.md` and the local iOS source. This is a source compatibility review, not an implemented adapter, live lifecycle test or rollout approval. Backend code and flags were not changed.

> **Latest status:** the owner-only ordinary adapter has now been reviewed; see the final follow-up section. The initial decision and implementation gaps below are retained as historical findings from before that adapter existed. ## Decision

The existing snapshot envelope is structurally compatible. The current iOS publishing implementation is **not integrated** with the new service. Heal Earth bearer transport exists for other account features, but Monographs still uses a legacy Notesnook user/token and API host. Keep branded links disabled and do not represent the installed app as supporting owned publishing yet.

## Heal Earth session transport: available, not wired to publishing

`apps/mobile/app/features/login/google-session.ts` stores an existing Heal Earth native session in iOS Keychain service `org.healearth.ohai.google-session`, accessible only while unlocked on this device. Its origin is `https://healearth.club/ohai`. Existing account/playback requests send `Authorization: Bearer <session.token>`, omit cookies, reject redirects and use a bounded timeout. This is a Heal Earth native credential, not a Notesnook sync token or raw Google OAuth token.

A dedicated publishing request wrapper can stay inside that private session boundary and target `/auth/native/monographs/capabilities`, `/v2`, the root PATCH path, and `/:noteId[/metadata]`. Do not use `requestOhaiPlayback` directly: it has a playback-only path allowlist. Match its account-change checks before work and after the response, including a fresh Keychain read and the selected `useOhaiAccount` ID. Never return the token to the editor WebView or send it to a viewer/redirect destination. Do not globally replace `Constants.API_HOST`: it also configures independent legacy services.

## Required client work before compatibility approval

1. **Route/auth adapter.** `packages/core/src/api/monographs.ts` currently requires `db.user.getUser()` and `db.tokenManager.getAccessToken()` and sends POST/PATCH/DELETE to `Constants.API_HOST`. Mobile database setup defaults that host to `https://api.notesnook.com`. The new adapter must use Heal Earth authentication and local note lookup; a disabled/unavailable Heal Earth endpoint must never trigger an upstream publish fallback.
2. **Account-scoped local state.** Existing publication records and `isPublished` are keyed by note ID alone. New owned-publication state must be scoped to Heal Earth account plus local note ID, separately from legacy records. Capture the chosen account for snapshot creation and discard/quarantine late responses after account changes. The request's legacy `userId` must not determine ownership.
3. **Stateful unpublish.** Existing `http.handleResponse` treats all 2xx JSON as successful, and `Monographs.unpublish` immediately removes its local record. A new adapter must inspect `ok` and `publicationState`: HTTP 202 `ok:false/unpublish_pending` retains a pending local record and retries the same note until the server confirms `ok:true/unpublished`. Disabled alias/listing is not proof that storage cleanup finished. The revised backend permits authenticated owner DELETE while publication rollout is disabled or membership consent has changed; the client must keep unpublish/retry reachable under those conditions. Authentication, ownership and rate limits still apply.
4. **Link readiness and legacy preservation.** Existing UI uses `metadata.publishUrl || saved.publishUrl` and ignores readiness. For an already complete `shareUrl`, require both rollout gates, `publicationState=published`, `aliasState=ready`, `shareUrlState=ready`, and canonical URL validation. For strict client-only keys, `shareUrlState=fragment_required` can instead permit local assembly from a validated `shareUrlBase` and the matching locally held key, under the same rollout/publication/alias checks. It is not permission to share the base alone. If the key is missing, or metadata is `legacy_or_missing`, pending/error or gated off, preserve the existing complete legacy link. Never replace a cached fragment-bearing URL with an unkeyed `publishUrl` or base. Keep passwords/fragments out of logs and diagnostics.
5. **Typed failures and retries.** Preserve 409/429/503 status, server `code`, `retryable` and state fields. The legacy HTTP error transformer does not preserve this full state contract. Retry the same account/note request after timeouts/busy states; do not create another source note or clear a known link. Validate response IDs against the requested note before storing results.
6. **Protected local-note flow.** Existing password recovery calls legacy `getMonographPasswordsKey`. Google-only/local users need an explicit first-party protected-password persistence strategy; do not assume the local attachment key also authorizes or implements this. Flush/re-read the selected note snapshot before publication and separately test unsaved edits, locked notes and local-only media.

## Fragment boundary — resolved in the revised contract

The original review identified contradictory no-server-key versus transient-fragment wording. The revised contract now distinguishes the modes accurately, and read-only inspection of `responseFor`, input validation and access checks confirms the corresponding source changes:

- Preferred native mode sends `hasFragment:true` and ciphertext, without `shareFragment`, a key-bearing header, or the decryption key. A ready edition returns a fragment-free `shareUrlBase`, `shareUrl:null`, and `shareUrlState:fragment_required`. The client validates readiness and both rollout gates, validates the exact HTTPS canonical origin/path, then appends its locally held `#key=...` before sharing. The service does not receive the key through this mode.
- Correlate the held secret with the authenticated account, source note, publication ID and edition revision; retain the same pending key on idempotent retries. A key from a different edition/account must not be attached to the base URL. Missing local key material must preserve the known complete link and prompt recovery, not expose an incomplete link.
- Send explicit `hasFragment` based on the current access mode when submitting a full update; `false` clears a previous fragment requirement when intentionally changing to a fragment-free edition. The server preserves existing fragment presence if both presence fields are omitted and rejects conflicting `hasFragment`/`shareFragment` values. Fragment-bearing editions remain ineligible for public listing and archive retention.
- Optional compatibility mode still accepts a body `shareFragment` or metadata header. If it contains a key, the authenticated service processes that key transiently. This is now explicitly disclosed as different from a strict client-only guarantee. The native implementation should use the preferred no-key transport mode.

This resolves the contract ambiguity; it does not implement local key management, authentication integration or the branded-link selector. The added backend tests described in the handoff were not rerun in this documentation review. No native release is authorized or implied.

**Compatibility conclusion:** the ordinary, unrestricted, revocable publication request and response are structurally compatible with the revised backend. The three original implementation blockers (first-party transport, account-scoped local state and HTTP 202 handling) have been addressed in this path. This is not approval for branded links, archive retention, protected native publishing, broader rollout or an installed build.

Confirmed from current source:

- `requestOhaiPublishing` stays inside the existing Keychain session boundary, sends the Heal Earth bearer plus `X-Heal-Earth-Account` to the exact first-party native route, rejects redirects, and compares both selected account and credential before/after the request. It preserves HTTP status, server code, retryability and publication state on errors. No upstream fallback was found in the owned adapter.
- Publication Keychain services are namespaced by validated Heal Earth account and local note ID. Account changes are checked around storage and responses. The legacy Monographs collection remains separate and is accessible only through explicitly labeled previous-publication management.
- The adapter resolves saved local note/content, rejects locked/deleted/vault notes and publishing while the editor page is open, checks for source modification during media preparation, and applies title/full UTF-8 payload limits. The submitted ordinary snapshot explicitly sets `selfDestruct:false`, `hasFragment:false`, `retention:revocable`, listing preference and `expectedRevision`. Current backend checks the revision after acquiring the edition lease and before changing access fields.
- Known protected, fragment-bearing or one-read editions are blocked from ordinary updates. Their native share controls are suppressed; unpublishing is still offered. No decryption key/fragment is transmitted by this ordinary path. Strict key-mode support remains a later native implementation.
- HTTP 202 `unpublish_pending` is parsed and retained in Keychain, with a visible Retry removal state. A successful no-existing-edition withdrawal is normalized to the requested note ID. Capability publishing-disabled does not disable the displayed unpublish action.
- The sheet now invokes `loadOhaiAccount` on entry and initially displays a saved-account check. Added UI tests model restoring a stored account before showing sign-in and keeping legacy management reachable without Heal Earth login. This supports the proposed restart fix; the coordinating chat must finish its real simulator/device restart acceptance.
- Ordinary links use only the pinned HTTPS reader origin and expected edition path. Branded URLs require both capability and response branded flags and a published/ready unrestricted record. Archive and protected-native controls are not exposed by this sheet.

### Remaining concerns to address or explicitly scope

1. **Fail closed on unknown access metadata before ordinary updates.** `parseOwnedPublication` treats absent or non-boolean `passwordProtected`, `hasFragment` and `selfDestruct` fields as false unless `restricted:true` is supplied. A published metadata response missing these fields can consequently appear ordinary; `publishOwnedNote` would then submit false access options. The current backend returns those booleans, but an incomplete/mixed-version response must not authorize downgrading access. Require a complete typed access descriptor (or preserve an unknown/restricted classification and block updates) for existing published editions. Keep this as a compatibility guard before relying on the adapter across server revisions; `expectedRevision` prevents stale writes but does not establish access-type knowledge.
2. **Restore cached withdrawal controls independently of capabilities refresh.** The sheet sets state only after `Promise.all([ownedCapabilities, refreshOwnedPublication])` succeeds. If capabilities fails but a cached publication or pending removal exists, the current UI shows an error without restoring Unpublish/Retry removal. Load account-scoped cached state first and allow metadata refresh to update it independently. New publication can remain disabled until capability validation succeeds; a capability failure should not hide a known revocation workflow.
3. **Retain a separate branded-link release check.** The present helper does not validate `caps.accountId === publication.accountId`, the current capability contract version, or `caps.publishingEnabled` when selecting a branded link. The component clears state in an account-change effect, but a future branded implementation should enforce those invariants at the link-selection boundary too. Branded flags are currently reported off, so this is a future branded-rollout requirement rather than a reason to enable anything now.
