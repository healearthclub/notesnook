# ohai Cloud Backup client package

This package implements the proposed version 1 encrypted envelope and the backup HTTP protocol. The inputs are already serialized Notesnook archive bytes. The application still needs to connect the export pipeline, validate and restore into a staged workspace, confirm recovery key storage and opt-in, and manage account credentials. Use synthetic archives until the payload and recovery design have passed review and on-device tests.

## Contributor map

- [`src/index.ts`](src/index.ts) defines the encrypted envelope and builds snapshot upload metadata.
- [`src/client.ts`](src/client.ts) defines the client HTTP requests and response types. For server-side parsing or storage changes, follow the [Worker map](../../servers/ohai-backup/README.md#contributor-map).
- Run `npm --prefix packages/ohai-backup test` from the repository root for client changes. For metadata shared across the client and Worker, also run `npm --prefix packages/ohai-backup run test:worker` after installing both packages' dependencies.

Report the first failing test, the relevant error, and the full-log path. See the [backup-metadata benchmark task](../../scripts/agent-benchmark/README.md).

Run `npm ci && npm test` from this directory. The tests cover a fixed vector produced independently with libsodium and Node's HKDF, key rewrapping, tampering, wrong accounts, and upload resumption after a lost response.

Install the dependencies in `../../servers/ohai-backup` and run `npm run test:worker` here to verify the actual Worker protocol with local D1 and R2. The test enables backup, commits ciphertext, restores from a second simulated device, denies access from another account, and revokes the restored device session on sign-out.

The local pilot also round-tripped a synthetic note's `.nnbackupz` export from the iOS simulator. The recovered ZIP matched byte for byte, and an isolated Notesnook Core database imported the note and reimported a web-labelled export. A separate local Worker run verified the full 50 MiB ciphertext limit. These checks cover archive transport and the shared Core format for one note. Browser runtime restore, attachments, vault coverage, and the iPhone memory budget remain to be verified.

## Format version 1

All integers are unsigned, big-endian 32-bit values starting at 1. The account identifier is the lowercase ASCII UUID supplied by the authenticated account service. The vault key and recovery secret each contain 32 random bytes from the host cryptographic RNG. A recovery key is `ohai1_` followed by the unpadded base64url recovery secret. It is generated by the client and should never enter a log or an API request.

- **Wrapped key**. The header is the ASCII marker `OHK1`, the key envelope version counter, a 32-byte random salt, and a 24-byte random nonce. Derive the wrapping key with HKDF-SHA-256 using the recovery secret, salt, and ASCII context `ohai/cloud-backup/v1/vault-key`. Encrypt the 32-byte vault key with XChaCha20-Poly1305 using that key and the header nonce. The associated data is the complete header followed by the account UUID. Encode the header plus tagged ciphertext as unpadded base64url and send it as `{formatVersion:1,keyVersion,envelope,previousKeyVersion}`. Rewrapping the same vault key changes the envelope version counter, while older snapshots keep their original version and remain readable. Suspected vault key compromise requires new vault key material and re-encryption.
- **Snapshot**. The header is the ASCII marker `OHB1`, the key envelope counter at upload, the portable archive format version, and a 24-byte random nonce. Encrypt the archive with XChaCha20-Poly1305 using the vault key and header nonce. Use the same associated-data construction. The transmitted bytes are the header and tagged ciphertext. The SHA-256 checksum in the HTTP protocol covers all those bytes. The key and archive format versions must match the caller's restore context before any plaintext is returned.
- **Limits**. The encoded snapshot is limited to 50 MiB including its header and authentication tag. The package accepts byte buffers. The iPhone memory budget and production payload limits still need device validation.

The [version 1 vector](test/vector-v1.json) provides all fixed inputs and expected wire output for another implementation. The wrapping KDF follows [RFC 5869](https://www.rfc-editor.org/info/rfc5869/). The encryption format uses [libsodium-compatible XChaCha20-Poly1305](https://doc.libsodium.org/doc/secret-key_cryptography/aead/chacha20-poly1305/xchacha20-poly1305_construction) with a random nonce for each message.

## HTTP client

Import `BackupClient` and `prepareBackup` from `@ohai/backup/client`. Prepare each snapshot once, hold on to its ciphertext and idempotency key, and retry using the same prepared object after a transport failure. A retry continues from the server's recorded upload status. The download helper verifies size and SHA-256 and decrypts before returning bytes to the caller. The application must validate those archive bytes and choose a staging workspace before any import.

Use the same-origin session cookie on web. A native caller supplies an access-token provider after its system authentication and Keychain flow are ready. The package requires a platform cryptographic RNG. The existing React Native entry point initializes `react-native-get-random-values`. Hermes runtime verification and secure device key storage remain integration work.

Use a separate ohai session lifecycle for Cloud Backup. The inherited Notesnook logout calls `db.reset()`. Its manual restore paths import into the active database and write attachment files afterward. Cloud restore needs a separate workspace and attachment staging so an interrupted restore can preserve the original workspace. The full export paths can also skip missing attachment bytes, so attachment completeness must be checked before the app reports a successful cloud backup.
